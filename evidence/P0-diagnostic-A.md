## Исходные ответы

### 1. HTTP и API

**Вопрос:** Как браузер взаимодействует с API? Как интерпретировать 401, 403, 409, 500?

> Браузер дает запрос, заголовок, тело. Если это какой-нибудь PUT или POST запрос, если GET, то только заголовок, забирает данные и уже отображает их браузере. HTTP статус 401 — это всё в ошибке. 400 — это всё ошибки сервера. 403 — это Forbidden. 500 — это ошибка уже клиента. Frontend должен реагировать на каждую из этих ошибок и определять их, и в соответствии с ошибками давать рекомендации, да, или указывать, что именно нужно исправить, чтобы не было ошибок.

### 2. UI State и Server State

**Вопрос:** Чем React UI state отличается от server state? Когда нужно инвалидировать кэш?

> Что отличается? То есть state. UI state — это state, который расположен в самом проекте, то есть локально. Server state — это состояние, которое сохранено на сервере. RTK Query кэширует данные, чтобы не приходилось каждый раз обновлять и, так сказать, чтобы не загружать проект, не ререндерить. Можно инвалидировать кэш, когда изменяется, например, при изменении имени пользователя должен произойти триггер и инвалидация должна произойти, и должно произойти изменение.

### 3. Проверка прав доступа

**Вопрос:** Где проверяются права доступа — frontend, backend, БД? Почему?

> Нужно проверять права доступа и на фронтенде, и в базе данных, и на бэкенде. Потому что фронтенд должен, так сказать, предупреждать о том, что нет права доступа. И если это, например, какая-нибудь атака, то и в базе данных тоже должна проходить проверка. На фронтенде недостаточно просто скрыть пользователя, потому что JS может показать её. Надо делать проверку на права доступа. Если он через POST нам направит и на бэкенде или в базе данных не будет никакой защиты, то он удалится.

## Разбор наставника после завершения самостоятельной попытки

- HTTP: коды 4xx относятся к ошибкам клиентских запросов и доступа; 5xx — к ошибкам сервера. Статусы 401, 403, 409 и 500 имеют разные смыслы и требуют подходящей обработки.
- RTK Query: кэш уменьшает число сетевых запросов и позволяет повторно использовать полученные данные. Инвалидация помогает обновлять устаревший серверный кэш.
- Права доступа: интерфейс может скрывать недоступные действия, но реальная авторизация обязательна на доверенной стороне.
- Webhooks: необходима идемпотентность по идентификатору события с надёжной уникальностью на уровне данных.
- Codex: важно проверять diff, тесты, ошибки, права доступа, безопасность и соблюдение архитектуры.
