## 1. API-контракт

**Метод и маршрут:** `GET /api/requests`.

**Необязательные query-параметры:** `search` (имя клиента), `status` (`new`, `in_progress`, `closed`; отсутствие фильтра — все статусы), `page` (номер страницы, по умолчанию 1), `limit` (размер страницы, по умолчанию 10). Backend фильтрует, сортирует по `lastMessageAt` по убыванию и возвращает страницу результатов.

Пример: `GET /api/requests?status=closed&page=3&limit=10`.

**Успешный ответ:**

```ts
type RequestStatus = "new" | "in_progress" | "closed";

interface RequestsResponse {
  items: {
    id: number;
    clientName: string;
    status: RequestStatus;
    lastMessageAt: string; // ISO 8601
  }[];
  page: number;
  limit: number;
  total: number;
}
```

При `total = 37` и `limit = 10` страниц 4; на последней 7 обращений. Поиск без совпадений — `200 OK` с `items: []`, а не `404`. Необходимо согласовать правила для некорректных номеров страниц и ограничение максимального `limit`.

**Ошибки:** `400` — некорректные параметры, `401` — не пройдена аутентификация, `403` — нет прав, `500` — внутренняя ошибка, `503` — временная недоступность. Сетевой сбой может возникнуть и без HTTP-статуса. В UI для временных сбоев предусмотрены объяснение и действие «Повторить».

**Доступ:** сервер проверяет действительную сессию / аутентификацию и права менеджера; скрытие UI на frontend не заменяет серверную проверку. Конкретный механизм сессии/token/cookie нужно отдельно согласовать с backend.

## 2. Схема React-компонентов и границы

- `RequestsPage`: читает `search`, `status`, `page` из URL; передаёт параметры в `useGetRequestsQuery`; распределяет данные и состояния дочерним компонентам.
- `SearchInput`: локально управляет вводом, использует debounce (ориентир 400 мс), сообщает о подтверждённом поисковом значении.
- `StatusFilter`: предоставляет выбор статуса.
- `RequestsList`: отображает полученные обращения и состояния пустой выборки/загрузки/ошибки по переданным данным.
- `Pagination`: отображает навигацию по страницам на основе `page`, `limit`, `total`.

При изменении поиска или статуса обновляется URL и `page` сбрасывается на 1. RTK Query делает запрос при изменении аргументов — вручную инвалидировать кэш только ради смены фильтра не нужно.

Для ссылки вида `/crm/requests?status=closed&page=3` параметры восстанавливаются при перезагрузке страницы. Фильтры в URL страницы и параметры запроса к API — разные сущности, их синхронизацию обеспечивает приложение.

Для первого запроса показывается загрузка; при смене фильтра можно использовать индикатор поверх старого списка с отключением действий или skeleton. У RTK Query `data` может содержать данные для предыдущих аргументов, а `currentData` — только для текущих.

## 3. Тестовые сценарии

**Сценарий 1 — загрузка:**
- Дано: менеджер авторизован; для теста backend содержит 37 обращений.
- Когда: пользователь открывает `/crm/requests`.
- Тогда: показываются первые 10 обращений, доступна навигация по 4 страницам, сообщение об ошибке отсутствует.

**Сценарий 2 — фильтр на третьей странице:**
- Дано: пользователь находится на `page=3`.
- Когда: выбирает статус `closed`.
- Тогда: URL обновляется до `status=closed&page=1`, выполняется запрос для первой страницы нового фильтра, список содержит только `closed` обращения.

**Сценарий 3 — ошибка сервера:**
- Дано: ответ API — `500`.
- Когда: пользователь открывает список.
- Тогда: отображается сообщение об ошибке и действие «Повторить», вместо некорректных данных; повторное действие инициирует новый запрос.

## 4. ADR: управление server state

**Контекст.** CRM требует получения обращений, фильтрации, пагинации, отслеживания загрузки и ошибок, а также актуальности серверных данных.

**Решение.** Для клиентской работы с данными используем RTK Query.

**Обоснование.** RTK Query даёт кэширование по аргументам, состояния запроса, повторное получение данных и инвалидацию кэша; меньше ручной инфраструктуры, чем при `fetch + useEffect + useState`.

**Ограничения.** Необходима Redux-инфраструктура и дополнительные зависимости. React-хуки RTK Query нельзя непосредственно использовать в React Server Components; в Next.js App Router они предназначены для Client Components. Использование RTK Query не означает отказа от передачи props и не заменяет серверное хранение данных.
