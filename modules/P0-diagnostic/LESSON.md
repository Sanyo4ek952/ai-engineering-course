# P0 — диагностический урок и тест учебного процесса

**Статус:** черновик, не начат.

## Зачем
Определить стартовый уровень и проверить, что обучающий процесс переживает глубокие ответвления и перенос в новый чат.

## Порядок и режим работы
Этапы выполняются последовательно: **А → Б → В** в течение двухнедельного пилота с ориентиром 6–8 ч/нед из `COURSE.md`. Указанные ниже длительности — ориентиры отдельных этапов, а не длительность всего пилота. До начала прочитать документы по списку из `README.md` и объявить критерии проверки.

- **А:** студент отвечает без AI и любых подсказок. Наставник предъявляет вопросы и фиксирует результат; ответы, подсказки и разбор разрешены только после сдачи и фиксации исходного результата.
- **Б:** сначала студент самостоятельно описывает решение без AI. После сохранения этой версии AI разрешён для теории, обсуждения, ревью и доработки; его вклад фиксируется отдельно. Итоговая защита — без AI и подсказок, разбор — после фиксации результата.
- **В:** AI разрешён для проверки учебного процесса и восстановления контекста; новые ответы за студента и неподтверждённые отметки о выполнении недопустимы.

## Часть А. Диагностика (40–60 мин)
Объясни устно или письменно, не используя AI:
1. Как браузер взаимодействует с API? Как интерпретировать 401, 403, 409, 500?
2. Чем React UI state отличается от server state? Когда нужно инвалидировать кэш?
3. Где проверяются права доступа — frontend, backend, БД? Почему?
4. Как защитить API от повторной обработки одного и того же webhook?
5. Какие действия ты выполняешь, прежде чем принять код, написанный Codex?

Сохранить исходные ответы и таблицу компетенций: «подтверждена / пробел / не проверена», ссылка на ответ и обоснование по `RUBRIC.md`. Проходного балла у диагностики нет.

## Часть Б. Практика (60–90 мин)
Спроектировать небольшую фичу «список обращений» с загрузкой, фильтрацией и ошибками. Артефакты:
- контракт API (запрос, ответ, статусы ошибок);
- схема компонентов и границы ответственности;
- минимум 3 тестовых сценария (включая негативный);
- короткое ADR: какой подход к server state выбран и почему.

На пилоте **не требуется** разворачивать всю CRM. Студент сам описывает решение до генерации кода.

Это небольшой урок пилота: после исходной попытки разобрать необходимую теорию, доработать артефакты и провести защиту из 2–4 вопросов без AI. Защиту или итоговую проверку оставить незавершённой для возобновления на этапе В. До начала объявить применимые критерии и веса по `RUBRIC.md`; реализация приложения не требуется. Сохранить исходную и итоговую версии четырёх артефактов, использованные запросы к AI и существенные изменения по его советам (либо отметить, что AI не использовался), ответы защиты и результат проверки с замечаниями. Не засчитывать навык только по исправленной с AI версии.

## Часть В. Проверка переносимости (15 мин)
1. Пока хотя бы одно действие урока ещё не завершено, задать дополнительный вопрос, не связанный напрямую с уроком. Сохранить вопрос, точку остановки, незавершённое действие и следующий шаг; предложить запись ответвления в `tracking/PARKING_LOT.md` без изменения программы.
2. Проверить имеющиеся результаты, согласовать патч `tracking/STATE.md`, применить его, сделать коммит и push и повторно проверить GitHub по порядку из `README.md`. Сохранить ссылки на доказательства и коммит; незавершённое действие оставить открытым.
3. Открыть новый чат проекта и дать доступ к GitHub без пересказа предыдущего чата. Прочитать документы из списка `README.md`. До продолжения попросить назвать фазу, текущий урок, последнюю подтверждённую проверку, незавершённые действия, блокеры и следующий шаг.
4. Сравнить все шесть пунктов с опубликованным `STATE.md`; сохранить ответ нового чата и результат сравнения. Проверка успешна, если все пункты совпали и не появились выдуманные завершения. При отсутствии доступа тест не засчитывать; при расхождении исправить причину и повторить проверку.
5. Возобновить сохранённое незавершённое действие и сохранить результат. Не засчитывать урок до проверки артефактов и ответов.

## Критерии завершения
В конце двух недель проверить и сохранить доказательства по каждому пункту:
- **А:** сохранены ответы на все 5 вопросов (или явный отказ/«не знаю») и статусы всех затронутых компетенций с обоснованиями; пробелы и непроверенные навыки перечислены отдельно.
- **Б:** сохранены исходные и итоговые версии всех 4 артефактов, минимум 3 тестовых сценария с хотя бы одним негативным, разбор теории, ответы на 2–4 вопроса защиты и проверка по заранее объявленным критериям. Для зачёта урока выполнены применимые условия `RUBRIC.md`; иначе указаны замечания и следующий шаг без отметки о завершении урока.
- **В:** сохранены одно ответвление, одно незавершённое действие и результат его возобновления; для теста нового чата сохранены число совпадений из 6, расхождения и итог повторной проверки, если она потребовалась. Успешный перенос — 6 из 6 без выдуманных завершений. Согласованный `STATE.md` опубликован и повторно проверен в GitHub.
- Сохранены фактические затраты времени за каждую из двух недель и явное решение студента: продолжать или исправить организацию пилота, с причинами и открытыми проблемами.

Пилот завершён как проверка процесса, когда все перечисленные доказательства собраны и решение принято; пробелы диагностики не мешают завершить пилот. Если урок не зачтён или тест переноса не прошёл, это фиксируется как результат пилота и основание для исправлений, без объявления этих заданий выполненными. Истечение двух недель само по себе не означает завершения.
