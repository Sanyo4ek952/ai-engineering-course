# API-CONTRACT.md — чтение списка обращений

**Урок:** M1-01 · **Версия:** 0.1 · **Статус:** DRAFT / совместно отредактирован, не утверждён backend.  
**Дата:** 2026-11-10. Маркировка: [С] — самостоятельная идея студента, [Н] — уточнение наставника, [С+Н] — смешанное решение. Это НЕ полный самостоятельный артефакт.

## 1. Метод и параметры

**[С+Н]** `GET /api/requests` — получение **списка**; фильтрация не изменяет данные в БД. Проверка и обновление статуса обращения выполняются отдельной мутацией (не частью этого метода).

| Параметр | Тип | Значение | Происхождение |
|---|---|---|---|
| `search` | string, optional | текст поиска по имени клиента | [С]; правило совпадения открыто |
| `status` | `new | in_progress | closed`, optional | без параметра — все статусы | [С+Н] |
| `page` | positive integer, optional | номер страницы, default `1` | [С+Н] |
| `limit` | positive integer, optional | записей на странице, default `20`, max `100` | параметр [Н], ограничение обсуждено с [С], значения [Н] |

**[Н]** Слишком большой `limit` (например, 1000000), отрицательная/дробная страница и неизвестный статус — `400`. `limit` не обязательно ограничивать только набором `10/20/50`; текущий контракт допускает целые `1..100`. Окончательный набор допустимых значений надо утвердить.

Пример:
```http
GET /api/requests?search=alex&status=new&page=1&limit=20
```

## 2. Успешный ответ

**[С]** Для пагинации нужны `items`, `page` и `total`; `limit` добавлен [Н].

```ts
type RequestStatus = "new" | "in_progress" | "closed";

type RequestsResponse = {
  items: Array<{
    id: string;
    clientName: string;
    status: RequestStatus;
    lastMessageAt: string; // ISO 8601
  }>;
  page: number;
  limit: number;
  total: number; // количество записей ПОСЛЕ применения фильтров
};
```

**[Н]** Поля элементов (`id`, `clientName`, `status`, `lastMessageAt`) ориентируются на проект P0 и подлежат согласованию с backend; выбор `id: string` для проекта пока предварительный. Не путать `total` с общим числом всех обращений без фильтра.

Пример (сокращённый):
```json
{
  "items": [{"id":"r-1","clientName":"Алексей","status":"new","lastMessageAt":"2026-11-10T10:00:00Z"}],
  "page":1,
  "limit":20,
  "total":57
}
```
В действительном ответе с `total=57` и `limit=20` на странице 1 может быть до 20 элементов; здесь оставлен только один для иллюстрации формата.

**[С+Н]** Число страниц вычисляется как `Math.ceil(total / limit)`. Студент правильно рассчитал 57 записей при limit 20: 3 страницы, на последней 17.

## 3. Пустая выборка и выход за последнюю страницу

**[С+Н]** Пустой результат — `200 OK` и `items: []`, не ошибка `500` и не `404`.

**[Н]** Запрос `page=100` с допустимыми параметрами, если всего 35 результатов, возвращает `200`, `items: []`, `page:100`, `limit:20`, `total:35`. Frontend может сразу вычислить последнюю страницу `Math.max(1, Math.ceil(total / limit))` и заменить URL на `page=2`, а не переходить через 99, 98 и так далее. При `total=0` остаётся страница 1 с пустым состоянием. Защита от повторного redirect и согласованность при изменениях данных должны быть проверены.

## 4. Ошибки

| HTTP | Когда | Что делает frontend | Авторство |
|---|---|---|---|
| `400` | неверный `page`, `limit` или статус | сообщает о некорректном запросе, не выдает это за отсутствие данных | [Н], после разбора со студентом |
| `401` | нет действительной аутентификации | прекращает показ защищённых данных, предлагает вход | [С+Н] |
| `403` | нет прав на данные | сообщает об отсутствии доступа, не показывает данные | [С] |
| `500` | внутренняя ошибка | показывает ошибку и возможность повторить | [Н]; первичный самостоятельный ответ студента ошибочно трактовал как пустой результат |

**[Н]** Пример формата ошибки (ещё требует согласования):
```json
{"error":{"code":"INVALID_PAGE","message":"page must be >= 1"}}
```
Нельзя считать этот JSON контрактом backend до согласования.

## 5. Доступ и безопасность

**[С]** Студент самостоятельно отметил, что сервер должен проверять авторизацию и права; интерфейс не заменяет серверную защиту.

**[Н]** Backend валидирует каждый входящий запрос (даже из Postman), проверяет сессию и доступ к организации, ограничивает `limit` и передаёт безопасные параметры в запрос к БД. База применяет запрос и собственные механизмы доступа, но не заменяет HTTP-валидацию backend.

**Открыто:** session cookie vs JWT, `HttpOnly`, `Secure`, `SameSite`, CSRF, модель ролей. Не фиксировать конкретную auth-схему в M1-01.

## 6. Границы и неутверждённые детали

- Семантика `search`, сортировка, ограничения длины поисковой строки.
- Нужно ли поддерживать только `limit=10/20/50` или диапазон `1..100`.
- Поля элемента обращения, форматы ID/даты и схема ошибки.
- Правила устойчивой сортировки при одинаковой дате, изменение набора данных между страницами.
- Статусы и контракт мутации изменения обращения — отдельное задание M1-07, не считать утверждёнными здесь.
